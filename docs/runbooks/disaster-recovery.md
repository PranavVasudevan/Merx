# Disaster recovery / backup runbook

Honest scope: this is a **local, single-machine reference architecture** (per the
project's zero-spend constraint — see `docs/architecture/BankLens-Master-Architecture-Plan.md`
§2). There is no multi-region failover, no replicated database, no on-call rotation
to page. What follows is the real recovery story for what actually exists today,
not aspirational enterprise DR theater. The master plan's §5.6/§11 describe what a
*production* deployment's DR would add (cross-site replication, PITR backups, chaos
drills) — this document is deliberately about the system as it is, not as it could be.

## What's actually at risk, and what isn't

| Asset | Recoverable how | RPO |
|---|---|---|
| `data/bronze/*`, `data/silver/*`, `data/gold/*` | **100% reproducible from source** — re-run the landing scripts (`run_vertical_slice.ps1`, `crosswalk.ps1`, `land_market_data.ps1`, etc.) against FDIC/SEC/Tiingo | effectively zero — it's a re-fetch, not a restore |
| `ml/deposit_flight/model_card.json` | Git-tracked (unlike `data/`) — restored by `git checkout`, or fully reproducible by re-running `scripts/deposit_flight.ps1` against the same landed 2022Q4+2008Q1 cross-sections | zero (in git) |
| `data/silver/crosswalk.json` | Regenerated by `scripts/crosswalk.ps1` (deterministic given the same FDIC+SEC inputs, modulo any upstream data revisions) | effectively zero |
| `mcp_audit_log` / `agent_runs` (Postgres, `platform/docker/docker-compose.dev.yml`) | **Not recoverable if the `pgdata` volume is deleted** — this is now the real system of record (see `libs/python/banklens_common/src/banklens_common/db.py`); back up via `pg_dump` if the history genuinely matters, or accept the loss (it's an audit trail, not source data) | none, unless backed up |
| `data/mcp_audit.jsonl`, `data/agent_runs/*.json` | Degraded-mode fallback only, used when Postgres is unreachable — not the primary store anymore. Not recoverable if deleted, but low-stakes (partial audit trail, not a system of record) | none — accept the loss |
| Source code (`pipelines/`, `services/`, `frontend/`, docs) | Git | zero, as long as commits are pushed to a remote |
| API keys (`.env`: `TIINGO_API_KEY`, `GEMINI_API_KEY*`, `ANTHROPIC_API_KEY`) | **Never backed up on purpose** — `.env` is git-ignored by design (see `SECURITY.md`). Re-obtain from each provider's console if lost. | n/a |

**The headline fact:** because Gold/Silver/Bronze all derive from public, re-fetchable
sources (FDIC, SEC, Tiingo) via idempotent connectors, "disaster recovery" for the
data layer is just "run the scripts again" — there is no database to restore from a
snapshot. This is a direct, deliberate consequence of the medallion architecture's
"Bronze is immutable and re-fetchable" principle (`docs/architecture/BankLens-Master-Architecture-Plan.md` §5.1).

## Recovery procedure — full rebuild from zero

If `data/`, the git repo clone, or the whole machine is lost, from a fresh clone:

```powershell
git clone <remote> banklens
cd banklens
copy .env.example .env    # then fill in your own keys (see .env.example comments)

# Core data (no keys needed — FDIC/SEC are public)
powershell -File scripts/run_vertical_slice.ps1 -Cert 3511
powershell -File scripts/run_vertical_slice.ps1 -Cert 6976
powershell -File scripts/crosswalk.ps1

# Feature 13's trained model (or just `git checkout` — model_card.json is tracked)
powershell -File scripts/deposit_flight.ps1

# Optional, needs your own free keys — see the relevant script's own docs
powershell -File scripts/land_market_data.ps1        # needs TIINGO_API_KEY
powershell -File scripts/land_sod.ps1                # keyless, FDIC SOD

# Verify
powershell -File scripts/run_tests.ps1
```

Expect `130 passed, 10 skipped` before landing data (the skips are the tests that
need it — see `CONTRIBUTING.md`), `140 passed, 0 skipped` after.

## Recovery procedure — a single corrupted/deleted Bronze partition

Bronze is partitioned by source/quarter/cert (`data/bronze/source=fdic/cert=6976/`,
etc.) — delete just the affected partition directory and re-run the one landing
script that produces it. Some feature CLIs also write a Gold-layer *report* to disk
as a cache (e.g. `data/gold/cert=6976.xray.json`, `data/gold/ma_fit.cert=6976.json`)
— these are convenience artifacts, not a system of record: every one is fully
reproducible by re-running the corresponding script (`run_vertical_slice.ps1`,
`ma_fit.ps1`, etc.) against the same Bronze, so recovery never requires more than
re-running one command per affected file.

## Recovery procedure — Kubernetes deployment

The cluster itself holds no unique state (see `platform/k8s/README.md` — the
`data-pvc` is populated by a one-shot loader pod from the same reproducible
sources, not a database). To recover:

```powershell
kubectl delete namespace banklens-dev   # if in a bad state
powershell -File scripts/k8s_dev_up.ps1  # rebuilds from scratch, ~2 min
```

## What real production DR would add (not built, and why)

Per the master plan's Phase 8 scope and this project's $0 constraint:
- **Cross-site object-store replication** — needs actual multi-region infra (cost)
- **Point-in-time recovery on a real database** — Postgres now holds real data
  (audit log, agent runs; see above), but there's no PITR/continuous backup, just
  the volume as-is. ClickHouse in `platform/docker/docker-compose.dev.yml` remains
  scaffolded, unused by any real code (see `platform/docker/README.md`)
- **Chaos drills, on-call runbooks, SLO-backed alerting** — meaningful once there's
  a real on-call rotation and paying users; premature for a reference build

These are honestly out of scope here, not silently skipped.
